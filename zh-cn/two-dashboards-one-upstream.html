IS-48 · 香港 · 15分钟 · 依赖关系梳理 · 可用性 · 共因失效

两块仪表板，有几条独立路径？

沿着路径查，别光数屏幕

微软的可靠性指南建议，分析故障时，应沿着用户操作流程梳理系统依赖关系。谷歌的SRE可用性附录区分了操作成功的比例和服务中断的时长。在这家虚构的体育馆，衡量的是能否提供可用的场地排期，而不是屏幕能不能亮。

课堂决策

在一次使用合成数据的隔离演练中，只要有一块可用的屏幕显示最新的场地排期，请求就算成功。体育馆的目标是让10,000次等权计数的排期请求中至少98.5%成功，而不是保证按时间计的正常运行率。各故障行互斥。除非情景明确另有说明，仍能运行的分支会显示正确的数据。

A（每周100港元）在主显示路径 P 旁增设备用显示路径，但两条路径都依赖原有排期数据源 F 和同一个传输网关 G。B（160港元）增加了独立的排期数据源 H，两块屏幕都能使用；按最初的条件，H 能在仅 F 故障时挽救260次请求。C（230港元）还为备用数据供应路径配备了独立的传输路径，在回放中能挽救仅 G 故障时的所有请求。这些都是虚构演示，不是测试实际运行系统的操作指引。

互斥的回放情景请求数
未发生任何受测故障9,400
仅主屏幕故障120
仅备用屏幕故障80
仅原有排期数据源 F 故障300
仅共享传输网关 G 故障100
你的决策

A、B 和 C 的请求成功比例各是多少？达到回放目标的方案中，哪个成本最低？指出 A 仍有哪些共享依赖。

第二轮 · 多了一项资料

采购方收紧了对数据新鲜度的要求。按新定义，在仅 F 故障的300次请求中，备用数据源 H 在 B 和 C 下都只能挽救230次。其他结果不变，包括 C 在仅网关故障时挽救的100次请求。不要跨行重复计数。

你的决策

重新计算 B 和 C 的成功比例，再选一次。B 至少要在仅 F 故障时挽救多少次请求才能达标？

有副本不等于有独立路径

在 A 方案下，一块屏幕故障时，另一块可以顶上：9,400 + 120 + 80 = 9,600，即96.0%。但 F 或 G 一旦故障，两块屏幕都帮不上忙，因为每条路径都依赖这两者。B 的备用数据源把成功请求数提高到9,860次，即98.6%；C 还挽救了仅 G 故障时的100次请求，达到9,960次，即99.6%。B 比 C 便宜，也能达标。

改变成功的判定标准

按收紧后的定义，B 的成功请求数为9,830次，即98.3%；C 为9,930次，即99.3%。只有 C 达标。B 需要在仅 F 故障时挽救9,850 − 9,600 = 250次请求，比现在多20次。这个结果取决于回放中各类情景的构成，并不是把各分支故障当作独立随机事件算出来的。

从头到尾检查整条路径

列出每条路径所需的条件：能正常工作的屏幕、能提供最新数据的数据源，以及可用的传输路径。请供应商提供证据，证明 H 不依赖 F，且 C 在没有 G 的情况下仍能传送排期。如果备用数据源在目标条件下无法提供最新的排期，就起不到有效的备份作用。

教师说明

让各组用“或”连接两块屏幕，再用“且”连接正常工作的屏幕、能提供最新数据的数据源和传输网关。然后让各组把共享节点移到“或”的范围之外。讨论实际试点如何仅通过经授权的隔离演练，估计更具代表性的各类故障所占比例。

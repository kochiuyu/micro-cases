IS-43 · 香港 · 15分钟 · 数据新鲜度 · 缺失值 · 运营状态 · 后备方案设计

实时数据断了，公交信息屏该显示什么？

公交数据接口返回的不只是预计到站时间

香港数字政策办公室通过资料一线通发布两家公交运营商的预计到站数据。其数据字典将数据生成时间与预计到站时间分开记录。其他公开的公交数据接口规范也同样区分观测数据的新鲜度与预测结果本身。下文的显示规则是虚构的。

课堂决策

香港一个交通信息团队正在测试一块电子公交信息屏。现在是14:00:00。时刻表涵盖所有线路，信息屏也会接收实时数据快照。附表中的快照已成功获取。团队要决定显示哪些预计到站时间，并统计有多少条线路拥有可靠的实时信息。

只有同时满足以下条件，才显示具体的实时预计到站时间：预测值不为空，该预测对应的观测距今不超过90秒，且预计到站时间不早于当前时间。若最新观测明确确认没有车辆在运行，这属于实时状态，而不是具体的预计到站时间。预测值为空，又没有这种确认，并不能证明该线路已经停运。

如果实时快照仍然够新，但某条线路没有可用的实时信息，就显示该线路在时刻表上的下一个时间，并明确标注为时刻表信息，而非实时信息。符合条件的预计到站时间或经确认的无车运行状态，都计入实时信息覆盖。用时刻表作为后备方案的，不计入。

第二轮 · 多了一项资料

到了14:01:30，四条事件记录仍然没有变化。网络检查依然能收到成功响应，但上游快照的时间戳最后一次更新是在13:59:50，距今已有100秒。没有新的运营信息可用。

如果上游快照距今超过90秒，就只显示一条“实时数据不可用”的横幅提示，不再显示该快照中的任何实时预计到站时间或状态消息。在收到新的快照且通过逐条线路的检查之前，使用附表中的时刻表时间作为后备方案，并明确标注。四个时刻表时间都还没到。

讲评 · 检查观测时间

在14:00，A的观测距今45秒，预计到站时间还没到，因此显示实时预计到站时间14:05。B的观测距今已有100秒，因此显示时刻表时间14:08。预计到站时间还没到，并不代表B的观测数据够新。

讲评 · 空白不等于零

C明确报告了无车运行，该状态距今20秒，因此显示这一状态，不显示预计到站时间。D没有能说明实时状态的证据，因此显示时刻表时间14:11。A和C两条线路有实时信息，覆盖比例为2/4，即50%。其中只有一条线路有具体的实时预计到站时间。

讲评 · 获取成功不等于数据已更新

在14:01:30，上游快照距今已有100秒。横幅提示和时刻表时间14:07、14:08、14:10和14:11取代所有实时信息。实时信息覆盖率是0/4，并不是四条线路都停运了。不能用过时的无车运行状态把时刻表上的发车时间藏起来，仿佛已经知道当前的运营状态。

讲评 · 两方面都要监测

分别就数据获取失败和距上游最近一次更新的时长设置告警。还要监测各线路的观测距今多久，以及实时信息覆盖情况；即使数据接口整体正常，个别线路的信息仍可能过时。恢复实时显示前，记录每次启用后备方案的原因。

教师说明

用四分钟分析第一个时点的情况，四分钟讨论故障处理规则，四分钟设计监测方案，再用三分钟讨论如何恢复。问问学生：恰好到90秒时怎么办？为什么刚收到的API响应不一定包含新的观测数据？这里的90秒规则和运营状态提示不是给实际运营商的操作指引。

来源与案例假设 · 选读

课堂决策所需的资料，上文已经齐备。来源只供选读，用来交代出处和背景。

线路ID、数值、时间、快照规则、后备方案规则和显示方式均为虚构。所列来源提供的是标准或数据集，不是实时班次预测，也不是运营商实际采用的后备方案政策。

  1. DATA.GOV.HK, DPO estimated arrival dataset。介绍两家运营商的数据来源，以及指定站点的预计到站时间。
  2. DPO, Bus Route List and ETA API Data Dictionary。分别说明初始数据的时间戳字段和预计到站时间字段，并未规定案例中虚构的显示方式。
  3. MobilityData, GTFS Realtime Reference。说明班次更新的时间戳有何含义，并将它与对未来到站时刻的StopTime预测区分开来。
  4. GTFS Realtime working group, Best Practices。说明有关刷新、数据距今时长和缺少更新时的建议，并非香港的API契约。
  5. Citybus, real-time Next Bus arrival data dictionary。运营商分别说明预计到站时间和数据生成时间戳，并未规定本案例使用的后备方案。

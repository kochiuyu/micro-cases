一件包裹，收幾筆費用？

一件包裹可以留下多筆電子記錄

GS1 EPCIS實施指南指出，同一批付運貨物在包裝、發運和收貨等環節可各自產生記錄。一筆事件記錄代表一個環節，不代表另有一批貨物付運。下文的香港速遞公司和數據均屬虛構，並未採用GS1標準。

課堂決定

在九龍一個虛構的速遞站，分析員Jo把包裹收費台帳與掃描事件記錄合併，供下午6時審核。台帳每件包裹只有一行，列出擬收費用，尚未開立發票。掃描資料每個事件佔一行，同一包裹識別碼可以合理地出現多次。

Jo須匯報台帳內所有包裹的擬收費總額，以及其中已核准開單的金額。虛構合約規定，每件包裹只可收費一次，而且必須在審核截止前至少有一筆有效的送達事件。若送達證據缺失、不足以確認送達或已被撤銷，該筆費用仍待審核，並非取消。

現有儀表板會把台帳的每一行與包裹識別碼相同的所有掃描記錄逐一配對，剔除沒有配對的包裹，再把結果中每一行的費用加總。下列記錄的鍵值均正確，無須按名稱配對，也沒有識別上的疑問。

包裹識別碼台帳費用（港元）初始快照中的事件
P17100已收件、已分揀、已送達 E31
P18100已收件、已送達 E40
P1980沒有掃描記錄
你的決定

你會按現況發布儀表板嗎？先算出儀表板顯示的費用總額，再重新計算擬收、核准開單及待審核的金額，不能漏掉任何包裹。

第二輪 · 多了一項資料

在同一個下午6時的截止時間前，系統收到P17的第二筆有效送達掃描記錄E42，也收到一筆經主管授權的更正：E43撤銷P18的送達事件E40。P18沒有其他送達事件。保留原有記錄，並註明E40已被撤銷。收費台帳沒有變動。

一位同事建議每件包裹只取最新一筆記錄；另一位則建議每個不同的收費金額只加一次。兩個做法都不會改變原有的收費規則。

你的決定

收到新記錄後，你會核准哪些費用開單，哪些留待審核？逐件包裹做哪些核對，你才會批准結果？為甚麼兩個簡便做法都不能作為通用方案？

講評 · 按包裹計算，不按掃描記錄計算

不要發布草稿。P17佔三行，P18佔兩行，P19則不見了。草稿的總額是 3 × 100港元 + 2 × 100港元 = 500港元。正確的擬收費總額是 100港元 + 100港元 + 80港元 = 280港元。即使聯結時保留未配對的包裹，只要仍按行加總，結果就會是580港元。

講評 · 逐件包裹作決定

從收費台帳入手。按更正記錄所指的事件，把已撤銷的送達事件排除在判定之外，但不要刪除記錄。逐件確認截至審核截止時是否仍有任何有效送達事件，然後為台帳內每件包裹列出一筆費用和一個狀態。初步核准P17和P18合共200港元的費用開單，P19的80港元則留待審核。

講評 · 先處理更正，再核准開單

E42為P17增加一項送達證據，而不是第二筆100港元的費用。E43使E40失效，P18因而沒有符合收費條件的送達事件。P19仍沒有掃描記錄。核准100港元開單，另有180港元留待審核。擬收費總額維持在280港元，100港元 + 180港元與該總額相符。

講評 · 不只核對總額，也要檢驗規則

只取最新一筆記錄，並非普遍適用的收費資格判定方法：較遲出現的分揀掃描記錄不一定會使有效的送達事件失效，而一筆更正只針對一個事件，不一定涵蓋該包裹的所有送達事件。若每個不同金額只計一次，P17和P18兩筆金額相同的費用便會合併為一筆。應按包裹識別碼分組，切勿按收費金額分組。

發布前，檢查台帳的識別碼是否全部有值且沒有重複，掃描和更正記錄的識別碼是否連結到正確的包裹及事件，以及有沒有例外情況被悄悄略過。輸出結果必須涵蓋台帳內每件包裹，每件只出現一次，並且只有一個狀態。逐筆對照來源核實金額，並確認無論逐件計算還是整體加總，核准開單金額加待審核金額都等於擬收費金額。

教師說明

預留15分鐘：4分鐘在紙上推演聯結結果，4分鐘核對初始金額，4分鐘判定更新後的狀態，3分鐘設計發布前的檢查。先問哪個表格每件包裹只有一行，再問用甚麼鍵值作聯結。

數字及事件代碼均為虛構。沒有掃描記錄，只代表缺乏送達證據，並不證明付運失敗。本練習不會改動任何實際收費，並假設所標示的更正具權威性。

所有包裹、員工、金額、收費條件、事件及截止時間均屬虛構。所引資料說明事件記錄和數據模型的做法，而非任何特定公司的送達或收費規則。

  1. GS1, EPCIS and CBV Implementation Guideline, release 2.0。說明同一批貨物在付運的不同環節如何產生多筆供追蹤的事件記錄，以及事件與付運本身在含義上有何不同。
  2. PostgreSQL, Table Expressions, §7.2.1.1。說明記錄如何逐行配對，以及左外聯結如何納入左側未配對的一行，而不會合併已有的配對結果。
  3. Ralph Kimball, Declaring the Grain。區分一行記錄所量度的內容與聯結表格所用的識別碼，並建議清楚說明每行代表甚麼。
  4. pandas, Merging and key uniqueness。說明如何驗證一對一及一對多的假設，並以重複鍵值為例說明驗證失敗的情況。
  5. SQLite, Built-in Aggregate Functions。說明為甚麼只加總不重複的收費金額，會令相同金額只計一次，即使費用分屬不同包裹也一樣。

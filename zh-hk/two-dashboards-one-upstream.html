IS-48 · 香港 · 15分鐘 · 依賴關係梳理 · 可用性 · 共因失效

兩個儀表板，有多少條獨立路徑？

沿路徑追查，不要只數屏幕

微軟的可靠性指引建議，分析故障時，應按用戶操作流程梳理系統的依賴關係。Google 的 SRE 可用性附錄區分操作成功的比例和服務中斷的時長。這個虛構體育館衡量的是能否提供可用的場地使用時間表，而不是屏幕有沒有亮起。

課堂決定

在隔離環境中進行的模擬演練裏，只要任何一個可用的顯示屏能顯示符合時效要求的時間表，請求便算成功。體育館的目標是在同等計算的 10,000 宗時間表請求中，至少有 98.5% 成功，而不是保證按時間計算的正常運作比率。表內各列故障情況互斥。除非情境另有明示，仍可運作的分支會顯示正確數據。

A（每星期100港元）在主要顯示路徑 P 之外增設備用顯示路徑，但兩條路徑都需要原有的排程數據來源 F 和同一個傳送閘道 G。B（160港元）增設獨立的時間表數據來源 H，兩個顯示屏都可使用；起初，H 可令 260 宗僅受 F 故障影響的請求成功。C（230港元）還為替代數據來源提供獨立的傳送路徑，令重播中所有僅受 G 故障影響的請求都能成功。這些是虛構示範，並非測試實際運作系統的指示。

採用 A、B 和 C 時，請求成功的比例各是多少？符合重播測試目標的方案中，哪個成本最低？指出 A 中哪些依賴項仍然共用。

第二輪 · 多了一項資料

買方收緊數據時效要求。按新定義，單是 F 故障所影響的 300 宗請求中，替代數據來源 H 只能令其中 230 宗成功，B 和 C 都一樣。其他結果不變，包括 C 在只有閘道故障時仍可令 100 宗請求成功。各列不得重複計算。

你的決定

重新計算 B 和 C 的成功比例，再作選擇。B 要達標，最少要令多少宗僅受 F 故障影響的請求成功？

有備份不等於有獨立路徑

採用 A 時，任何一個顯示屏故障，另一個都可補上：9,400 + 120 + 80 = 9,600 宗，即 96.0%。但 F 或 G 一旦故障，兩個顯示屏都無法補救，因為每條路徑都依賴 F 和 G。B 的替代數據來源令成功請求增至 9,860 宗，即 98.6%；C 還能令 100 宗僅受 G 故障影響的請求成功，達 9,960 宗，即 99.6%。B 比 C 便宜，亦能達標。

改變成功的判準

按收緊後的定義，B 有 9,830 宗請求成功，即 98.3%；C 有 9,930 宗，即 99.3%。只有 C 達標。B 須令 9,850 − 9,600 = 250 宗僅受 F 故障影響的請求成功，比現時多 20 宗。結果取決於重播中各種情況的構成，而不是把各分支的故障視為互相獨立的隨機事件。

從頭到尾檢視路徑

記下每條路徑所需的條件：正常運作的顯示屏、符合時效要求的數據來源，以及可用的傳送路徑。要求供應商提供證據，證明 H 不依賴 F，而 C 即使沒有 G 也能傳送時間表。如果替代數據來源無法在目標條件下提供符合時效要求的時間表，就不是有效的後備。

教師說明

請各組繪圖，用「或」連接兩個顯示屏，再用「且」連接正常運作的顯示屏、符合時效要求的數據來源和傳送閘道。然後請各組把共用節點移到「或」的分支結構之外。討論實際試行時，如何只透過獲授權的隔離演練，估算更具代表性的故障分佈。

來源與個案假設 · 選讀

課堂決策所需的資料，上文已經齊備。來源只供選讀，用來交代出處和背景。

整個重播均屬虛構；故障標籤和比率不代表任何實際運作的系統、供應商承諾或保安測試。

  1. Microsoft Azure, failure mode analysis。說明如何沿用戶操作流程追蹤所經組件，找出依賴關係和故障點。
  2. Google SRE, availability table appendix。說明為甚麼對於只有部分功能可用或負載不均的服務，統計失敗請求的宗數有參考價值。
  3. AWS, Availability and Beyond。透過討論故障隔離和鬆散耦合，解釋共用依賴項為甚麼可能限制系統的韌性。
  4. AWS Builders’ Library, Static stability using Availability Zones。工程例子區分哪些範圍彼此獨立，以及系統受損時能否繼續運作。這並非關於虛構體育館的證據。
  5. Microsoft Azure, reliability testing。說明如何在可靠性測試中驗證關鍵流程，以及服務能否在功能受限時維持在可接受的水平。

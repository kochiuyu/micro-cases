IS-26 · 香港 · 15–20分鐘 · 冪等性 · 交易識別 · 回應不明

兩次確認，一張訂單？

操作成功後，回覆仍可能遺失

公開的API文件說明了呼叫方未收到可用回應時，應如何控制重試。關鍵在於分辨：是重試原本打算進行的操作，還是發起另一項操作？以下預訂情境純屬虛構，並非服務供應商的事故報告。

課堂決定

一家虛構的香港手工藝工作坊主辦機構，正檢視即將推出的預訂工具。每張訂單預留一個可轉讓的名額。客戶可以用同一帳戶、同一工作坊及相同聯絡資料，為朋友另訂一個名額，這是正常操作。以下例子的名額均充足。工具不收取款項，但確認預訂仍等於承諾提供一個名額。

客戶按下「確認」後，有時只見畫面上的載入圖示一直轉動。伺服器可能仍在處理，可能已預留名額，也可能尚未受理請求。單看畫面，無法分辨是哪種情況。團隊要訂定重試規則，而不是改變預訂資格或取消有效訂單。

方案 A 對每次獲受理的提交都建立一張新訂單，包括逾時後的重試。方案 B 在首次提交前分配一個固定的請求識別碼；重試同一筆原定訂單時沿用該碼，如訂單已完成，便顯示原有結果。另設明確獨立的「另訂一個名額」操作，使用時會產生新的識別碼。兩個方案都可在已有撥款的發布工作範圍內完成。B 需要額外的狀態管理和測試；A 較簡單，但重複下單的後果要由支援人員處理。如果未能通過正確性檢查，可以延後發布。

逾時只說明客戶沒有收到甚麼，不一定反映伺服器做了甚麼。無論是帳戶及工作坊資料相同，還是點擊次數，單憑任何一項都無法確定客戶原本想預訂多少個名額。

你的決定

預訂工具應把每次重試當作新訂單，還是以固定識別碼辨認原有請求？請說明你的規則如何保留真正獨立的另一筆預訂。

第二輪 · 多了一項資料

一項受控的發布前測試補足了缺失的事實。Lin 只想預訂一個名額。她首次提交時已訂到名額，但回覆延遲了。二十秒後，她選擇「重試」，仍然只是想完成原來那筆訂單。另一方面，Sam 在首筆預訂確認後，特意選擇「另訂一個名額」：他想為兩位朋友訂兩個名額。Sam 的兩筆訂單在帳戶、工作坊、數量和聯絡資料欄位上完全相同。這些意圖已在測試中核實，並非從相似的記錄推斷出來。

在擬議的 B 方案中，Lin 首次提交和重試均使用識別碼 L1。Sam 的兩筆獨立訂單分別使用 S1 和 S2。這些簡短代號只供課堂說明；正式運作時產生的識別碼須避免碰撞，亦不含個人資料。識別碼的適用範圍以已通過身分驗證的帳戶和建立預訂的操作為限。若沿用現有識別碼卻更改數量或工作坊，系統會拒絕該請求，留待處理，而不會在沒有提示的情況下重用原有結果，或視作新訂單。

擬議的服務契約規定，自首次受理起保留重試識別碼及相應結果48小時。所有測試嘗試均在一分鐘內進行。這是虛構的設計假設，並非供應商的保證。尚未確定結果的請求若接近或超出這段期限，須核對預訂狀態，而不是自動另發識別碼。訂單仍在處理時，介面會顯示「處理中」，並提供查詢狀態的選項，而不是承諾再提供一個名額。重試狀態到期後，仍以現有預訂記錄為準。

你的決定

工具應如何處理 Lin 的重試和 Sam 的兩筆預訂？請訂明識別規則、結果未明時的應對方式，以及一項能揭示設計不安全的測試。

計算下單意圖，而非嘗試次數

按 B 方案，Lin 獲得一筆預訂，並收到該筆預訂的原有結果；Sam 則獲得兩筆獨立預訂。因此，三個下單意圖帶來三個名額。若四次提交都獲獨立受理，A 方案便會預留四個名額。若把資料相同的訂單一律合併，兩位客戶合共只會獲得兩個名額，Sam 正當的第二筆訂單也會被錯誤剔除。這些是按指定測試輸入得出的結果，並非對缺陷率的估算。

把識別規則寫入服務契約

要履行個案所述的承諾，應選 B。首次發送前便要產生並保留識別碼，不要只因回覆緩慢而換碼。預訂完成後，應顯示預訂參考編號，並清楚區分「重試這筆訂單」和「另訂一個名額」。冪等性是指重試同一項原定操作不會多出一筆預訂，並不表示每則訊息只會送達一次，或每次回應都一模一樣。客戶仍須能按新的意圖下單。

保護不只在按鈕，更在交易邊界

記下識別碼與正式寫入預訂，必須一同成功或一同失敗。使用同一識別碼的並行提交，不可各自通過獨立檢查並各訂一個名額。結果仍未確定時，應查詢狀態，或沿用同一識別碼按規則重試，而不是另作預訂。若無法使用識別碼記錄庫，應暫停或核對狀態，而不是在沒有提示的情況下略過保障。維持正常的帳戶授權規則：持有識別碼並不等於有權查閱其他客戶的預訂。

測試以下情況：預訂已正式寫入但回覆遺失、兩份相同請求同時提交、識別碼相同但欄位有變、兩個不同識別碼的欄位完全相同，以及接近到期時狀態仍未確定。除了畫面，還要查核名額記錄。若日後加入發送確認通知或其他下游操作，這些操作也要各自設有防重複措施；單靠防止重複建立預訂，不能保證只發出一封電郵或只收取一次款項。

一個合理的異議

B 增加了儲存和處理並行請求的要求，介面亦須更清楚地顯示各種狀態。若未能驗證這些保障措施，與其聲稱重試是安全的，不如延後發布，並透過獲授權的狀態查詢處理結果未明的請求。若系統刻意只接收不具約束力的查詢，並在作出任何承諾前由人手核對，A 可以是可接受的方案，但這樣便改變了本個案即時確認名額的承諾。停用按鈕可減少誤按，卻無法處理回覆遺失或從另一個連線階段發起的重試。

教師說明

在介紹兩位客戶的情況之前，先請學生訂明識別規則。第二輪資料會挑戰兩種看法：「每按一次就是新訂單」和「資料相同就是重複訂單」。課堂應聚焦於業務意圖、以甚麼記錄為準，以及如何驗證承諾，而不是背誦 HTTP 標頭。系統遷移個案討論新舊系統之間的轉移；本個案只有一套預訂系統，同一項操作的請求可能重複送達。實體防錯措施有助使用介面，但不能取代伺服器端的交易識別。不要求進行任何實際預訂、付款或正式系統變更。

來源與個案假設 · 選讀

課堂決策所需的資料，上文已經齊備。來源只供選讀，用來交代出處和背景。

主辦機構、客戶、時間和設計細節均為原創虛構設定。每張訂單預留一個可轉讓名額，同一帳戶可下多張訂單，名額充足，亦不收取款項。Lin 有一個下單意圖，提交了兩次；Sam 有兩個下單意圖，也提交了兩次。正確結果是三個名額；若每次提交都獨立處理，便會產生四個；若把相同資料合併，則只剩兩個。所有嘗試均在一分鐘內進行。保留四十八小時是個案訂明的契約條款，並非業界標準。重試狀態到期後，現有預訂記錄仍會保留。若請求結果仍未確定，不論尚待處理還是已過期，都須核對狀態，而不是不經查證就建立預訂。公開來源說明技術原則和不同供應商各自的服務契約；沒有任何一項能證明虛構的實作已通過測試。

  1. RFC 9110, section 9.2.2: Idempotent Methods。說明重複執行時的預期效果，並提醒在操作不具備適當語義時，不應自動重試。這並不表示所有 POST 操作都具備冪等性。
  2. Amazon Builders’ Library: Making retries safe with idempotent APIs。解釋為甚麼相同參數可以代表不同意圖、如何識別呼叫方的請求，以及為何應以不可分割的方式一併記錄識別碼和執行相關變更。
  3. Stripe: Idempotent requests。記載各 API 版本在重試時如何重用原有結果，以及請求鍵的產生方法、參數比較和保留期限。個案並未照搬 Stripe 的服務契約。
  4. PayPal Developer: Idempotency。說明操作即使逾時也可能已成功，以及如何使用 API 支援的請求識別碼查詢狀態；是否支援及保留多久，視乎 API 而定。
  5. Adyen: API idempotency。記載適用範圍、有效期、並行請求和暫時性錯誤的處理方式。跨區域限制及各供應商特有的限制，說明為甚麼服務契約必須訂明。
